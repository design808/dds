# DDS 페이지 구성 기준

DDS는 버튼·입력·상태 표현과 조작 방식을 맞춘다. 화면의 목적, 정보 순서와 서비스 문구는 해당 서비스에서 결정한다. 컴포넌트 원본을 사용했다는 사실만으로 사용하기 좋은 화면이 완성되지는 않는다.

## 원본에서 유지할 것과 선택할 것

| 구분 | 적용 방법 |
| --- | --- |
| 디자인 규격 | 글자 역할, 크기, 패딩, 경계, 모서리, 포커스, 아이콘과 상태 표현은 원본·공식 variants를 사용한다. |
| 필수 구조 | 라벨과 입력의 연결, 탭과 패널, 메뉴 트리거와 패널, 폼과 제출 버튼의 관계를 유지한다. |
| 선택 콘텐츠 | 설명, 글자 수, 상태, 날짜, 배지, 보조 행동은 필요한 항목만 넣는다. `optional`과 실제 콘텐츠를 사용한다. |
| 견본 콘텐츠 | 예제 제목·이름·안내 문구·개수·날짜·여러 개를 나란히 보여주는 배치는 복사하지 않는다. |
| 페이지 구성 | 그리드, 섹션 순서, 본문 폭과 관련 정보의 묶음은 실제 작업과 콘텐츠에 맞춘다. |

검색창 아래 설명은 모든 검색에 필요한 요소가 아니다. 라벨과 placeholder만으로 충분하면 생략한다. 정해진 입력 형식이나 검색 범위를 추가로 알려야 할 때만 도움말을 넣는다. 결과 개수는 결과 제목 옆 한 곳에서 표시하고 검색창 아래에서 반복하지 않는다.

## 목록·탐색 화면

- 검색·분류·필터·정렬·결과가 서로 가까운 하나의 흐름이 되도록 배치한다. 각각을 큰 섹션으로 벌리지 않는다.
- 입력 즉시 결과를 바꾸는 방식과 버튼으로 검색을 실행하는 방식 중 하나를 선택한다. 두 동작을 별개로 제공하면 각각의 목적을 구분한다.
- 카드에서는 제목과 선택에 필요한 조건을 먼저 보여준다. 채용공고라면 기업·직무·지역/경력·마감일을 우선하고 산업·등록일·부가 태그는 필요에 따라 생략한다.
- 개수는 실제 결과에서 계산한다. 선택한 필터, 결과 없음, 초기화와 새로 불러오는 상태를 함께 설계한다.
- 반복 목록의 열 수와 정보량은 실제 긴 제목과 마지막 행으로 확인한다. 좁은 화면은 내용의 우선순위를 유지하며 한 열로 바꾼다.

## 작성·편집 화면

- 같은 목적의 필드를 한 묶음으로 두고 라벨·도움말·오류를 해당 필드에 붙인다. 필드 사이 구분선을 모든 곳에 넣지 않는다.
- 필수 표시, 입력 제한과 글자 수는 실제 제출 규칙과 연결한다. 견본의 `maxlength`, 날짜, 체크 상태를 서비스 기본값으로 사용하지 않는다.
- 작성 후 실행할 행동은 작성 흐름 마지막에 둔다. 길어서 고정 행동이 필요하면 본문을 가리지 않도록 공간을 확보한다.
- 오류는 문제가 있는 필드와 복구 방법을 안내한다. 모든 저장·검증에 상단 Alert나 모달을 반복하지 않는다.
- 모달 본문에는 폼·목록·설명 중 필요한 내용을 넣는다. 예제의 문서 미리보기 상자까지 감싸지 않는다.

## 상세·결과 화면

- 주 제목, 핵심 상태, 본문, 다음 행동의 순서를 먼저 정한다. 모든 텍스트를 같은 크기·굵기로 표시하지 않는다.
- 긴 본문과 결정에 필요한 요약 정보는 구분한다. 보조 열이 필요 없는 화면에 빈 사이드바를 만들지 않는다.
- 차트는 사용자가 비교할 값과 단위를 먼저 정하고 형태를 고른다. 장식용 수치·비율·완료 상태를 넣지 않는다.
- 카드 경계는 반복 항목이나 독립된 정보 묶음에 사용한다. 모든 제목·문단을 카드로 감싸지 않는다.

## 화면 검수

1. 처음 보는 사람이 화면의 목적과 주요 행동을 바로 찾을 수 있는가?
2. 라벨·placeholder·도움말·버튼이 같은 내용을 반복하지 않는가?
3. 목록에서 항목을 고르기 전에 불필요한 메타정보를 너무 많이 읽어야 하지는 않는가?
4. 내용이 짧거나 길어져도 묶음과 간격이 유지되는가? 320px·390px·PC에서 확인했는가?
5. 검색 결과 없음, 오류, 대기, 선택 후와 키보드 이동이 자연스러운가?
6. 컴포넌트 CSS를 바꿔 해결한 것처럼 보이게 한 부분은 없는가? 공식 크기·변형·선택 콘텐츠부터 확인한다.

기존 서비스 리디자인에서는 새로 구성한 화면과 원래 서비스의 필드·이벤트·권한·제출값도 함께 대조한다.
