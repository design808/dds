# 화면 설계와 검토

## 화면의 일부터 정하기

화면을 그리기 전에 다음 질문에 짧게 답한다. 답은 구현의 기준이며 공개 사이트에 문서 섹션으로 노출할 내용이 아니다.

- 누가 어떤 상황에서 사용하는가?
- 이 화면에서 완료할 주 작업과 이어지는 화면은 무엇인가?
- 지금 결정에 필요한 정보와 상세에서 보여줘도 되는 정보는 무엇인가?
- 실제 콘텐츠의 양과 긴 경우는 어느 정도인가?
- 요청 대기·실패·빈 값·완료·권한 제한에서 사용자는 무엇을 할 수 있는가?

기존 화면이 있으면 원래 콘텐츠와 동작을 조사한다. 새 서비스라면 제공되지 않은 브랜드나 이전 제품의 화면을 전제로 삼지 않는다. 추측이 필요한 경우 서비스 목적에 맞는 작고 완결된 범위를 선택한다.

## 레퍼런스에서 읽을 것

시각적 표현이 필요한 소개 화면과 작업 효율이 중요한 서비스 화면을 구분한다. 실제 참고 화면을 볼 때는 색상이 아니라 다음 관계를 관찰한다.

- 첫 시선과 주요 행동을 어떻게 연결하는가?
- 탐색·검색·필터·결과가 서로 얼마나 가까운가?
- 본문과 보조 정보의 비중이 사용자의 결정에 맞는가?
- 강조, 여백, 반복 항목의 밀도가 정보의 중요도와 맞는가?
- 작은 화면에서 무엇을 유지하고 무엇을 접는가?

참고 자료의 구성을 그대로 복사하지 않는다. 현재 콘텐츠와 목적에 도움이 되는 관찰만 적용한다. 업종 이름이나 검색 순위만으로 특정 구조를 선택하지 않는다.

## 구조를 선택하는 기준

대안이 필요하면 실제 제목·목록·폼 내용을 유지한 채 영역의 관계를 바꿔 비교한다. 예를 들어 검색 결과가 중요한 화면에서는 필터 위치·목록 형태·상세 접근을 비교할 수 있다. 소개 화면에서는 핵심 메시지와 시각 자료의 비중, 주요 행동으로 이어지는 순서를 비교할 수 있다.

선택한 배치가 주 작업을 더 빨리 이해시키는지, 필요한 정보를 덜 반복하는지, 모바일에서도 자연스럽게 이어지는지 판단한다. 한 가지 안을 선택한 뒤 그 안의 위계와 밀도를 다듬는다. 구성 이유가 없는 장식과 모든 항목을 같은 카드로 감싸는 방식으로 빈 공간을 채우지 않는다.

콘텐츠를 새로 작성할 수 있는 경우에도 확인하지 않은 고객·수치·보장·실제 연결 상태를 만들어 넣지 않는다. 실제 기능의 진행과 결과는 서비스에서 관리한다.

## DDS와 페이지 CSS의 경계

| DDS에서 유지 | 페이지에서 설계 |
| --- | --- |
| 저장한 색상·제목/본문 서체·라이트/다크 값 | 콘텐츠와 서비스에 맞는 정보 순서 |
| 컨트롤 높이·글자·내부 패딩·색·경계·모서리·상태 | 가용 폭·페이지 그리드·외부 여백·필요한 영역 높이 |
| 버튼·아이콘·달력·팝업의 공식 고유 크기와 조작 | 어떤 컴포넌트·변형·선택 콘텐츠가 필요한지 |
| 필수 HTML·라벨·aria 관계 | 허용 슬롯의 실제 내용·링크·서비스 이벤트 |

프로필 값은 프로젝트가 저장한 파일에서 읽는다. 자료의 추천 색상이나 폰트를 적용하지 않는다. 입력·목록·탭 본문은 부모 폭을 채우고, 모달 폼은 본문 폭을, 2열 폼은 각 셀의 폭을 사용한다. 문서의 440px 제한·가운데 정렬·축소·견본 미디어 프레임과 예시 이름·도움말·날짜·항목 수를 서비스 기본값으로 쓰지 않는다.

`component-layout.css`는 `ui/dds.css`에 포함되어 있으므로 별도로 로드하지 않는다. 문서 전용 `component-specimens.css`는 SDK 묶음에 포함하지 않는다. 스크롤 영역의 높이가 필요하면 부모의 `--dds-scroll-height`·`--dds-scroll-max-height`를 사용한다. 기본값은 `auto`·`none`이다.

컴포넌트를 변경한 화면에서는 기본 상태만 보지 않는다. 사용하는 변형과 선택·초점·열기 상태, 긴 문구, 320px·390px·PC의 실제 컨테이너를 확인한다. 탭은 항목이 가용 폭을 넘을 때의 가로 이동만 허용하고, 활성 밑줄이나 초점 때문에 세로 스크롤이 생기면 원인을 수정한다. 문서 미리보기와 별도로 문서 CSS를 로드하지 않은 서비스 화면에서도 확인한다. 스크린샷만으로는 넘침과 키보드 동작을 확인할 수 없으므로 실제 브라우저의 크기·스크롤·초점도 검사한다.

서비스 헤더는 전체 폭에 연결하고 내용의 최대 폭(좌우 여백 포함)·여백은 부모의 `--dds-topnav-content-width`·`--dds-topnav-gutter`로 정한다. 하단 경계를 내부 콘텐츠 너비로 제한하거나 `100vw`로 부모를 벗어나게 하지 않는다. 테마 전환은 푸터에 아이콘 버튼 하나로 두고 상태별 기능 이름과 hover·키보드 탐색 툴팁을 연결한다. 기존 provider·저장 키를 재사용한다. 모달의 제목·본문·행동 간격은 원본을 따르며 문서 견본의 상하 margin을 복사하지 않는다.

## 브라우저에서 판단하기

먼저 전체 화면을 보고 주 작업과 중요한 정보가 보이는지 확인한 뒤, 개별 요소의 정렬과 간격을 본다. PC·좁은 모바일과 레이아웃이 바뀌는 경계, 부모 폭 240·320·510·800px의 Grid/Flex에서 확인한다.

- 첫 화면에서 읽기 시작할 곳과 다음 행동이 명확한가?
- 같은 내용을 제목·라벨·도움말·버튼에서 반복하지 않는가?
- 페이지가 비어 보인다면 정보의 배치가 문제인지, 필요한 콘텐츠가 없는지 구분했는가?
- 읽어야 할 정보의 양에 맞는 행·열·본문 폭을 선택했는가?
- 긴 문장·오류·빈 목록·선택 후에도 묶음과 흐름이 유지되는가?
- 모달의 전체 폭 필드와 2열의 각 필드가 부모 폭을 사용하는가?
- 실제 이미지·영상 슬롯에 견본 프레임이나 고정 폭이 남지 않았는가?
- 이동·입력·팝업·키보드·초점 복귀가 화면 구성과 일치하는가?
- 내부 규격·상태는 DDS 원본의 계산값과 같고, 외부 폭·여백·영역 높이는 서비스에 맞는가?

시각 검토와 기능 검사를 구분해 기록한다. 관찰한 결함은 수정하되 단순히 변화를 주기 위해 배치를 계속 바꾸지는 않는다. 전체 화면을 직접 보지 않았다면 시각 검수가 완료됐다고 말하지 않는다.
